# v1 分阶段实施 Spec

状态：产品方向已确认，工程接口为实施契约；未标已完成的能力均为待开发。关联 [产品契约](../product-contract.md) / [架构](../architecture.md)。

## S1：JD 更新前置

### S1a 本地更新计划器

新增 `jobagent.jd_update.build_update_plan`，输入本地 freshness 看板与现有搜索配置，输出明确的收藏、搜索、旧详情三个阶段预算。纯本地计算，不导入平台或模型。库存达到 300 条也必须保留新轮计划，不让收藏占用搜索额度。旧详情按“想投 / 再看”优先排序，只选择到期的详情复核任务；列表复扫另外列示，不混入详情预算。

输出只表示 planned / not_run：包含生成时间、历史库存、实际搜索来源、选中岗位 ID、未纳入本轮的详情数与复扫数。不得填充虚假的成功数。关闭和归档岗位不进入详情队列；配置城市或关键词缺失时明确阻断搜索阶段，不凭空扩大范围。支持命令 `py -m jobagent.jd_update --db output/jobagent.db`；数据库以只读方式打开，freshness 的迁移/同步在内存副本执行，不改变个人数据库。

验收：库存超旧目标仍计划新轮；两来源预算独立；优先级、去重、终态排除、零预算与非法预算正确；部分旧数据覆盖明确；源数据库内容未改变；只生成计划，无 Boss/模型调用。

### S1b 统一更新任务与审阅入口

用户操作：更新监管显示上次更新、本轮预算、当前来源和待复核数量；点击“更新岗位”启动。摘要常驻，参数和完整明细可折叠。任务运行时可停止；刷新页面不丢进度、不重复启动。

拟定 API：

| 请求 | 行为 |
|---|---|
| `GET /api/job-updates/plan` | 只计算本地计划，返回到期量、来源、预算；不触发 Boss 或 AI |
| `POST /api/job-updates` | 校验参数、原子获得浏览器租约、持久化任务后返回 202 与 run_id；冲突 409 |
| `GET /api/job-updates/{run_id}` | 返回总任务、各来源/阶段、计数、停止原因及未完成项 |
| `POST /api/job-updates/{run_id}/stop` | 设停止请求，当前读取安全结束后停；不得新开下一阶段 |

执行顺序：登录与会话预检 → 新收藏 → 搜索新岗位 → 到期详情复核（想投/再看优先）→ 本地汇总。每阶段有独立预算，默认收藏 25、搜索 25、旧详情 20；用户可调整。搜索沿用配置的关键词/城市，显示此次实际覆盖来源。

接入新轮采集时，保留旧 `run(target=库内总数)` 兼容接口，为每来源独立计算本轮起始库存与预算，禁止直接使用旧目标 300；收藏从第一页发现新增，达到额度仍执行搜索。一个 CDP 连接内串行执行，并记录真实 source。额度计量为新增库存记录（含失败占位），另列成功详情数。收藏有页数上限；未完整走完列表不能标记完整覆盖。安全停止不得继续下一来源。

任务状态：queued → running → completed / partial / paused / failed / cancelled；重启遗留 running 标记 interrupted，显式恢复新任务且链接原任务，不后台自动联网。completed 只说明选定任务项完成，另列全库剩余量与覆盖范围。安全警告和登录失效暂停全部后续阶段。

指标必须分别展示：新发现、详情成功、详情失败、旧 JD 已变/未变/确认关闭、未覆盖来源、剩余到期项。列表未见不等于岗位关闭；失败不清空旧 JD。旧采集与简历驱动采集必须接入同一执行互斥。

验收：GET 无外部调用；双击/跨入口并发不重复启动；停止、重启、部分失败可追溯；已有人工决定不被改写；有覆盖说明；桌面/窄屏实际视觉检查。真实 Boss 更新单列验收，不用 mock 通过冒充更新成功。

## S2：岗位分析与三套方向

输入为 S1 后的有效 JD 快照和明确导入的 Word 基准。可先看部分数据结果，但必须显示样本日期、覆盖不足及无效项，不能把部分更新称作全量市场结论。

规则过滤与 AI 理解分离。输出每岗需求、匹配证据、差距、建议及三个方向的样本数和代表岗位。重算键包含 JD 内容、确认档案、模型和提示词版本；未变复用。用户确认三个方向后进入 S3，不代替用户确认方向。

验收：无事实依据的成果不能进入输出；同输入不重复分析；新档案不覆盖人工拒绝；用户可绕过推荐低分；模型失败可见且不污染上次有效结果。

## S3：三套 Word 和长图资产

导入只在明确确认时发生；保留原 Word、抽取事实与版本。三套 Word 基于同一基准保守调整，先供用户编辑确认，再转换 PDF 和长图。三份不按单个 JD 重写；无页数硬限制，但图片需满足平台实测大小/清晰度约束。

验收：正文事实与基准可核对；原文档保留；中文、分页、图片清晰度逐份检查；Word 修改产生新版本；旧审核包不悄悄替换图片。目标平台尺寸能力未实测时不声明发送可用。

## S4：招呼语与审核包

AI 输入完整 JD、确认事实、三套资产摘要与用户偏好；输出招呼语、推荐资产和理由。UI 摘要常驻，完整 JD/证据/差距可展开；默认可直接编辑招呼语、切换简历并预览实际长图。v1 不再显示逐岗自动改写简历为主流程。

包冻结岗位及招聘者身份、JD 版本、文本、基准及资产版本；内容修改生成新版本并使旧确认失效。请求生成失败保留旧有效包且清楚说明未发送。仅模型生成“与岗位有关”不足以展示“已验证匹配”。

## S5：受控首次沟通

发送前检查当前目标、岗位有效性、资产和审核版本，并封闭旧自动发送入口。一次用户点击授权该岗位该包的文本和长图。事务创建唯一执行任务，持久化动作后执行；重复点击返回同一任务。

文本与图片动作分别使用 pending / running / confirmed / failed / unknown。先检查已有动作证据，再继续未完成步骤；确定未发送才最多重试一次。安全、身份异常或未知状态不自动重试。图片上传必须核验实际会话附件，不把选择文件成功视为送达。

验收：重复点击、断网、进程退出、文本成功图片失败、平台限制、会话变更均不重复发送。模拟测试通过后才进行最多 3 岗真实试点，每岗用户点击。实测文字和长图均出现在正确会话才通过该岗位验收。

## S6：进展同步与人工接管

主动同步相关会话，保留证据、时间和变更历史；AI 不确定结果待确认，人工修正不被下次推断直接覆盖。沟通进展与招聘结果独立。提示用户接管后续回复、正式投递和联系方式，不自动发送。

## 开发与交付规则

每阶段先冻结边界、测试再实现、独立审查后记录证据。持久化迁移幂等且非破坏；测试使用临时库和注入平台/模型，不访问个人会话。真实外部验收需与本地结果分开记录。先完成 S1，再按依赖推进；不把整个路线图一次性打包开发。
