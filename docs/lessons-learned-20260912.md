## 一、浏览器自动化与 Playwright 资源管理

### 1.1 Playwright 驱动进程泄漏导致浏览器导航全局卡死（最严重，当日 5 次异常的唯一根因）

问题描述：发送功能执行若干次后，浏览器所有新页面导航（page.goto）开始零响应超时，连非目标网站（example.com）也无法打开；但已打开页面内的 fetch 请求全部正常。症状先后表现为"找不到沟通按钮""goto 30 秒超时"，极易误判为目标网站限流。

原因分析：Playwright 架构为 Python 代码 → node.exe 驱动进程（翻译官）→ CDP 协议 → 浏览器。发送服务 OutreachSendService.close() 只关闭了数据库连接，从未调用 sender.close() 释放 Playwright 连接。每次执行发送泄漏一个持有浏览器 CDP 会话的 node 驱动进程，5 次执行积压 5 个，叠加 MorseTools 外壳与 cdp-proxy 共十几个客户端挤占同一条控制通道。导航必须经过该通道且需新开渲染进程，被挤死；fetch 走已存活渲染进程的通道，故幸存。

解决方案：
1. 代码修复：OutreachSendService.close() 中补调 sender.close()（提交 cc97e24）。
2. 现场处置：taskkill 清掉 5 个泄漏驱动进程，导航 0.62 秒即恢复。
3. 验证闭环：修复后完整执行一次发送，结束后系统内驱动进程数回归到 1（仅其他系统合法持有的那个）。

可复用经验：
- Windows 上使用 sync_playwright().start() 的封装类，必须保证 close() 真正执行且调用链完整，code review 时把"资源释放链"当作必查项。
- 多个 CDP 客户端共用一个浏览器时，任何一个客户端泄漏都会拖垮全局，排查时先数进程数。
- 判断"浏览器卡死"的快速方法：看驱动进程（node run-driver）数量是否随使用次数单调增长。

标签：Playwright, 进程泄漏, CDP, 资源生命周期, Windows

### 1.2 "疑似限流"的分层排查方法论（fetch 对照实验）

问题描述：导航超时后，初步归因为"Boss 限流、访问频率过高"。用户质疑：最初以更快速度采集 JD 时从未出问题。归因被推翻。

原因分析：限流假设未经对照验证。目标网站限流作用于服务端，若真被限流，同会话同 Cookie 的任何请求都应受影响。

解决方案：在已打开的页面内用 fetch() 直接探测（同源、同 Cookie、不触发导航）：首页 553ms、详情页 190ms、detail.json 接口 97ms，全部 200——服务端完全健康；再对比导航层（超时、零响应），将问题锁死在 CDP 客户端层，最终定位驱动泄漏。

可复用经验：
- 排查异常先做分层对照实验，再下结论：服务端层（页内 fetch 测响应码与耗时）→ 凭证层（Cookie 完整性）→ 客户端层（裸 CDP 与 Playwright 行为对照）。
- "频率过高"是最偷懒的归因，必须用数据反驳或证实：列出当日实际请求时间线，与历史成功期对比。
- 导航零响应 + 页内 fetch 正常 = 客户端控制层问题，与服务端无关，直接排查浏览器调试通道。

标签：排查方法论, 限流, fetch对照, 分层诊断

### 1.3 浏览器级导航与 Playwright 导航的区分实验

问题描述：需要证明问题不在浏览器本身。用裸 CDP HTTP 接口（PUT /json/new?url=...）开新标签页导航 example.com，一次成功；同一时刻 Playwright goto 同站超时。

原因分析：浏览器原生导航正常说明渲染进程派发、网络栈均健康；Playwright 侧挂起说明其 CDP 会话被污染（泄漏驱动挤占）。

解决方案：将"裸 CDP /json/new"纳入排查工具箱，作为区分"浏览器问题 vs 自动化客户端问题"的判据。

可复用经验：Chrome 远程调试端口的 /json/new、/json/list 是免费的判据来源，不消耗目标网站请求；排查浏览器自动化问题先做这组对照。

标签：CDP, 判据实验, Playwright

### 1.4 测试桩需与真实驱动协议同步演进

问题描述：修复引入新参数（wait_for_selector 的 state="attached"、page.context 属性）后，既有 FakePage 测试桩批量报错。

原因分析：测试桩是真实浏览器行为的低配仿真，真实协议新增用法时桩必须同步；且桩的行为默认值（如点击沟通后同页跳转）要与真机实测结论一致（Boss 实际新开标签页）。

解决方案：FakePage 增补 context 属性、selector_calls 记录、on_click_chat_btn 钩子；默认行为对齐真机结论。

可复用经验：每次真机事故修复后，回归用例必须同时覆盖"事故场景"与"桩的协议同步"；测试桩默认行为应来自真机实测而非想象。

标签：单元测试, 测试桩, 回归用例

## 二、Boss 发送链路安全设计

### 2.1 安全校验页误判：URL 防伪参数引发发送误停

问题描述：首次真实发送瞬间被判"检测到安全校验"而停止，实际什么都没发生。

原因分析：Boss 普通页面 URL 会带 _security_check=<时间戳> 防伪参数，与真正的安全校验页 URL（/web/user/safe/verify）特征重叠，字符串匹配误伤。

解决方案：SECURITY_URL_MARKERS 移除 _security_check= 子串，仅保留真实校验路径特征；并补单测锁定"带防伪参数的普通 URL 不算校验页"。

可复用经验：URL 特征匹配要区分"路径标识"与"查询参数装饰"；对拦截类判断宁可放宽检查、用页面内容做二次确认。

标签：URL匹配, 误判, 发送安全

### 2.2 岗位已关闭的识别、异常建模与状态回写

问题描述：发送时目标岗位已下线，系统不认识该状态，报错误导排查方向；死岗信息也不回流数据库。

原因分析：发送链路缺少"岗位关闭"这一业务状态：页面关闭标记（职位已关闭/已停止招聘/该职位已下线）未识别；异常体系中无 JobClosed 类型；freshness 表不回写。

解决方案：boss_sender 识别 CLOSED_JOB_MARKERS 后抛 JobClosed（SendFailed 子类，属"确定未发出"）；服务层捕获后写 job_freshness（evidence_state=closed），停止任务剩余动作；更新计划的复核队列自动排除 closed 岗位。

可复用经验：外部状态变化要建模为独立异常类型并区分"确定失败/未知/暂停"三态，回写到唯一真相源，让全链路决策基于事实。

标签：异常建模, 状态回写, 死岗处理

### 2.3 残留聊天页复用导致跨会话误发（当日最严重的业务事故）

问题描述：第二次自动发送把另一家公司（五世科技）的招呼语和简历图发进了前一公司（轮动科技）的聊天会话，客户收到两轮不相关内容。

原因分析：发送器存在"当前已是聊天页就直接返回"的快捷路径；上一次发送残留的聊天标签页（属于轮动科技的会话）被直接复用，新会话内容被输入到错误窗口。快捷路径缺乏任何"会话对象与目标职位一致"的校验。

解决方案（三道防线）：
1. 删除快捷路径：每次发送强制从职位详情页进入，点沟通入口打开会话。
2. 身份校验：打开会话后用投递包中的职位名（前12字）与公司名（前5字）轮询匹配会话头部 8 秒，不匹配即在输入任何内容前拒发（SendFailed）。
3. 同任务会话缓存：同一任务内第二个动作（简历图）复用已校验会话，避免重复导航。

可复用经验：对"会对外发出内容"的自动化动作，必须有独立于流程正确性的"目标身份校验"最后防线；任何 shortcut 在浏览器自动化里都是隐患，残留状态一律不可信。

标签：误发事故, 身份校验, 发送安全, 最后防线

### 2.4 沟通入口新开标签页的跟进

问题描述：点击"立即沟通"后 Boss 新开 /web/geek/chat 标签页，发送器留在职位详情页上等聊天输入框，15 秒超时，招呼语未发出。

原因分析：_ensure_chat 假设点击后聊天界面在当前页打开，未处理新标签页情形。

解决方案：点击前后对比 context.pages 中聊天页集合，跟进新开的聊天标签页（更新工作页引用），后续输入与上传都在新页执行。

可复用经验：浏览器自动化的页面流转假设必须真机验证；"点击后新开 tab"是国内站点常见模式，处理点击类动作时要跟踪 context.pages 变化。

标签：页面流转, 新标签页, Boss聊天

### 2.5 隐藏 file input 的等待方式

问题描述：简历长图上传一直报"未找到聊天图片上传控件"，但选择器实际能匹配到元素。

原因分析：图片上传的 input[type=file] 是隐藏控件（视觉不可见），Playwright wait_for_selector 默认等待 visible，永远超时。

解决方案：改用 state="attached" 等待元素挂载即可，set_input_files 对隐藏控件同样有效。

可复用经验：file input 天生隐藏，等待策略必须用 attached；遇到"选择器能查到但 wait 超时"优先怀疑可见性门槛。

标签：Playwright, file input, 等待策略

## 三、数据更新与新鲜度管理

### 3.1 登录判定双标准（cookie 优先原则）

问题描述：同一浏览器，发送预检判定"已登录"，采集器判定"未登录"并失败，互相矛盾打断用户操作。

原因分析：发送预检用 CDP Cookie 检查（wt2），采集器用 DOM 选择器（8 秒超时）。页面渲染慢时 DOM 探针误报；DOM 选择器还随站点改版腐化。

解决方案：统一以 wt2 Cookie 为唯一主判据，DOM 选择器降级为辅助，cookie 缺失时退避重试（2s/4s/8s）后才允许 DOM 兜底。

可复用经验：同一事实的判定必须全系统同源；登录态判定用凭证（Cookie/Token）而非页面元素，页面元素只做兜底。

标签：登录判定, Cookie, 双标准

### 3.2 TTL 与实测死亡率脱节

问题描述：岗位详情采后 1-3 天内死亡率极高（实测 9/13），但未审阅 core 岗复核周期 7 天，复核之前岗位已死，系统仍显示"就绪"。

原因分析：新鲜度 TTL 拍脑袋设定，未按真实死亡率校准。

解决方案：core 岗 TTL 7 天收敛到 3 天，贴住高发死亡窗口；TTL 参数集中管理并注释校准依据。

可复用经验：所有"过期/刷新周期"类参数都要用实测数据校准；死亡率高的数据源，复核周期必须小于死亡窗口。

标签：TTL, 数据新鲜度, 参数校准

### 3.3 reject 岗位自动复核浪费预算

问题描述：用户已明确放弃的岗位仍按 30 天周期进入自动复核队列，浪费复核预算。

原因分析：复核队列只看 TTL 与状态，未尊重用户的显式决策。

解决方案：interest=reject 的岗位 refresh_attention/action/due 全部抑制，更新计划（要求 refresh_due）自动排除；展示层保留记录但不消耗预算。

可复用经验：用户的显式负决策优先级高于任何自动策略；自动队列必须显式排除被人工否决的条目。

标签：复核预算, 用户决策, 队列过滤

### 3.4 死岗吃掉复核预算（候补递补机制）

问题描述：detail_refresh 复核 20 个岗位，其中死岗被"消耗"后本轮净产出趋零。

原因分析：计划只有主列表，关闭岗位不计入产出也没有替补。

解决方案：生成计划时带 backup_job_ids（预算等量的候补池）；执行时实测关闭数 N，自动从候补池补 N 个。

可复用经验：高死亡率的批处理任务必须设计候补池，替补数量以实测失败数封顶，保证净产出。

标签：候补递补, 净产出, 批处理设计

### 3.5 预算不可配置与失败原因不透明

问题描述：更新预算硬编码 25/25/20，界面无展示不可调，用户原话"根本没有什么可选的"；任务失败只显示四个字"任务失败"。

原因分析：计划参数未进配置层，失败诊断信息（stop_reason、各 action error）只写库不上面板。

解决方案：预算进 config.yaml（update_budgets）+ 面板数字输入框（留空用默认值，POST 时服务端注入）；失败时面板直接显示 stop_reason 与建议动作。

可复用经验：用户可见的调参项进配置+界面双通道；错误信息必须带着"下一步建议"到达用户面前，不能让用户去翻日志。

标签：可配置化, 错误透明化, 用户体验

## 四、长任务可观测性与节奏控制

### 4.1 停止粒度：阶段级 → 条目级

问题描述：更新任务停止只在阶段边界生效，单阶段 20 条采集中途无法停，用户只能等或杀进程。

原因分析：stop_requested 检查在阶段循环之间，未传入采集循环。

解决方案：采集器 run_incremental/refresh 接受 should_stop 回调，每个条目处理前轮询；触发后抛 CollectionStopped，已采部分保留，阶段记 cancelled、任务记 cancelled。备份递补阶段进度累计首轮计数。

可复用经验：长任务的停止粒度必须到条目级；已完成的功不可弃，停止语义要区分"未开始/进行中已完成部分保留"。

标签：停止粒度, 优雅中断, 任务语义

### 4.2 进度推送：已采 n/预算 m

问题描述：长任务执行期间界面只有"任务执行中"，无法判断在跑还是卡死，只能手动刷新。

原因分析：无进度回调链路，执行器与面板之间没有中间态。

解决方案：采集器每条完成后回调 progress(collected, budget)；执行器写入计划的 stage.progress 并持久化；面板执行期间每 4 秒轮询，状态行显示"旧 JD 复核 已采 7/20"。

可复用经验：可观测性三要素：条目级进度、服务端持久化中间态、前端自动轮询。三者齐备才能杜绝"卡死还是在跑"的猜测。

标签：进度推送, 可观测性, 自动轮询

### 4.3 固定沉睡与自适应等待

问题描述：详情页采集每条固定沉睡 8-15 秒等待渲染，与页面实际响应无关，一轮 20 条浪费数分钟。

原因分析：用固定 sleep 模拟"等页面渲染好"，没有利用真实就绪信号。

解决方案：轮询 JD 内容选择器或关闭标记出现即继续，总时长封顶 6 秒，另加 0.8-2 秒随机人性化停顿；配置 adaptive_wait=false 可回退。条目间防风控的随机节奏保留不变。

可复用经验：等待渲染用"信号 + 封顶"替代"固定时长"；防风控的节奏随机化和"等就绪"是两件事，不能混为一谈。

标签：自适应等待, 渲染就绪, 防风控节奏

### 4.4 发送节奏与失败重试的间隔管理

问题描述：连续发送多家公司、失败后立即重试并反复诊断性重访，短时间高频打开目标站详情页。

原因分析：发送服务无跨任务间隔控制；失败后的诊断行为（反复开页面）加重负载。

解决方案（建议项，待实施）：不同公司发送强制随机间隔 3-6 分钟；同一岗位失败后至少等 10 分钟；失败后禁止诊断性重访。

可复用经验：对外部站点的自动化动作要全局节流而非单任务节流；失败后的第一反应是离线分析，不是立刻再碰对方页面。

标签：发送节奏, 全局节流, 重试策略

## 五、工程运维与调试方法论

### 5.1 调试端口双绑定与进程清理

问题描述：8765 端口旧服务进程残留，SO_REUSEADDR 允许新旧进程同时监听，请求打到旧代码，改动"不生效"。

原因分析：HTTPServer 默认允许地址复用；kill 后未验证端口实际释放。

解决方案：重启流程固化为"netstat 查 LISTENING PID → taskkill /F → 再查确认单监听 → 启动 → 复测接口"。

可复用经验：凡改代码必重启+必验证"当前跑的是新代码"（可用接口返回特征验证）；监听端口清理要核对 PID 而非假设 kill 成功即干净。

标签：端口占用, 进程清理, 部署验证

### 5.2 Windows 编码与环境坑

问题描述：netstat 子进程输出 GBK 乱码导致解析失败；heredoc 脚本中文输出偶发异常；诊断进程偶发被 SIGTERM 无输出。

原因分析：Windows 子进程默认 GBK 编码、Python stdout 编码随环境变化、外部进程管理不可控。

解决方案：subprocess 输出统一 decode('gbk', errors='ignore')；长脚本用 io.TextIOWrapper 强制 UTF-8 并 -u 无缓冲运行；诊断输出落盘文件再读取；被 SIGTERM 时换脚本文件方式重跑。

可复用经验：Windows 自动化脚本必须显式处理编码；重要诊断输出落盘而非依赖 stdout；进程异常死亡时用"输出文件是否存在且完整"判断执行进度。

标签：Windows, 编码, SIGTERM

### 5.3 发送账本的可审计修正

问题描述：误发事故后，账本中任务状态为 confirmed（已确认送达），但实际送达对象错误，直接重发会被防重复机制拦截。

原因分析：账本记录"系统做了什么"而非"业务上是否正确"，状态机没有"作废重置"路径。

解决方案：人工修正流程：UPDATE 任务状态 queued + stop_reason 注明事故原因与时间、动作 attempts 清零 pending；保留原始记录可追溯；重发后账本继续正常记账。

可复用经验：状态机要预留"人工修正"通道，修正必须留痕（stop_reason 写明原因），防重复机制与账本状态解耦考虑；修正前后各查一次状态并输出留档。

标签：账本修正, 可审计, 状态机

### 5.4 测试与真实验收的分层纪律

问题描述：一次修复后系统自报 confirmed，但实际发错会话——"独立验证"只查了文本在页面可见，未校验会话归属。

原因分析：验收标准停留在"系统证据存在"，未回到业务事实（发给谁、内容对不对）。

解决方案：确立三层验收：系统证据（账本 confirmed+evidence）→ 页面事实（真实聊天页文本、送达标记、输入框为空排除草稿）→ 会话归属（会话头部公司/职位与目标一致）。本日轮动事故的独立验证补充了第三层。

可复用经验：自动化系统的"成功"必须用独立通道验证，且验证维度要包含"业务对象正确性"，不只是"动作完成性"。

标签：验收纪律, 独立验证, 业务事实

## 核心经验教训 Top 5

1. 资源释放链是浏览器自动化的第一隐患：封装类 close() 必须调用链完整到达 Playwright stop()，用"执行 N 次后驱动进程数不增长"作为回归检查项。
2. 异常归因先分层对照再下结论：服务端（页内 fetch）→ 凭证（Cookie）→ 客户端（裸 CDP vs Playwright 对照），"限流/频率"假设必须有数据支撑。
3. 对外发出内容的动作必须有目标身份校验最后防线：打开的会话/窗口/表单要与业务对象（公司、职位）匹配，不匹配宁可拒发。
4. 每个真实事故 = 一个回归用例：测试桩随真实协议演进，事故场景用例防止同类复发。
5. 系统自报成功 ≠ 业务成功：验收要回到真实页面核对"发给谁、发了什么"，输入框为空排除草稿假象，送达标记确认投递。
