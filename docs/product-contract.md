# 产品契约：个人求职投递代理 v1

状态：根据用户已确认需求冻结；2026-09-10。实现进度以 [阶段记录](development-stage.md) 为准。

## 目标与顺序

在本机完成岗位收集、岗位理解、求职决策、逐岗审核后的首次沟通。先更新 JD，再分析岗位方向，确认三套通用简历，最后打通招呼语与简历长图发送。第一批最多 3 个岗位，每个岗位单独点击发送。

## 已确认的产品边界

| 环节 | v1 契约 |
|---|---|
| 数据更新 | 用户主动点击“更新岗位”，获取新增收藏和搜索岗位，复核到期旧 JD；打开页面不访问 Boss |
| 分析 | 分析有效 JD，优先处理“想投 / 再看”；规则负责明确硬条件、去重、有效性，AI 负责需求理解、事实匹配、差距与建议 |
| 增量 | 新增或内容变化才重新分析；模型、提示词或用户确认的档案版本变化时，相应分析可失效 |
| 人工决定 | 推荐分数是建议，用户可坚持投递；岗位关闭、目标不明等执行阻断不能覆盖 |
| 历史拒绝 | 保留原决定及原因；能力变化可以提示重新考虑能力不匹配的岗位，不覆盖薪资、公司、工作方式等拒绝 |
| 简历基准 | 用户明确选择“以这份 Word 为新基准”后才导入；不监听文件改动自动替换，不凭文件年龄判定事实过期 |
| 三套方向 | 根据更新后的 JD 池提出三个方向及名称，用户确认后再生成；不提前指定方向 |
| 简历编辑 | 复制已确认 Word，保留事实、结构和用户措辞，保守调整排序与重点；用户可继续编辑并确认，不限制一页或两页 |
| 资产 | Word → PDF → 简历长图。PDF 是中间态，实际发送长图；用户确认具体资产版本 |
| 招呼语 | 自我介绍 → JD 的一个具体需求 → 真实相关成果 → 作品集 → 自然收尾；不拼接多个项目堆砌术语，不虚构案例 |
| 作品集 | 每家公司均可提及简历中的作品集；网址和展示内容必须来自已确认事实 |
| 审阅 | 可看完整 JD、适配证据和差距、可编辑招呼语、可切换三套简历、可预览实际长图 |
| 发送 | 用户逐岗点击一次“发送招呼语和简历长图”即授权当前快照；系统完成打开对话、上传和发送、核验，无第二次隐式确认 |
| 后续沟通 | 正式投递、交换联系方式、持续回复交回人工；系统不自动回复 |
| 进展 | 用户点击“同步沟通进展”后读取相关会话，记录来源、时间、证据和历史；推断不确定时待确认，可人工修正 |

沟通进展（未联系、已打招呼、对方已回复、沟通中、已发简历、已约面）与招聘结果（进行中、已拒绝、已结束、已录用）独立记录，不能实现成必须依次经过的流水线。长图可能早于回复发送。

## 发送不变量

- 用户修改招呼语、所选简历或资产内容后，旧审核快照失效；点击发送时原子锁定岗位、收件人、文本和资产版本。
- 文本和图片分别记录未尝试、执行中、已确认成功、确定失败、结果未知。部分成功仅补齐缺失部分。
- 只有明确未发送的普通失败可自动重试一次；结果未知先核对证据，不能盲目重发。
- 登录、验证码、安全警告、岗位或收件人身份异常立即暂停。不得通过刷新、切换会话或试探速率规避。
- 数据库、日志、真实简历和登录信息不入 Git。外部服务错误不得伪装成本地成功。

## 后续版本

逐 JD 微调简历、更深入的公司背调、更强的个性化决策可后续增加。v1 不跟踪未结项项目，不做多人权限系统，不自动添加联系方式。
