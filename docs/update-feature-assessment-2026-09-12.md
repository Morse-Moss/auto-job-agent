# 数据更新功能评估与改进方案（2026-09-12）

评估对象：S1 更新岗位链路（jd_update.py 计划 / job_updates.py 运行台账 / job_update_executor.py 执行 / boss_collector.py 采集 / freshness.py 新鲜度规则），结合 9 月 12 日真实事故（9/13 可投岗位已关闭、更新运行因登录误判失败）。

## 总体结论

链路的安全设计是好的：计划只读、执行需显式调用、浏览器租约互斥、暂停不自动恢复。核心缺陷是新鲜度判定纯靠时间周期，缺少"使用时校验"，导致库存死亡率高达 70%（9/13）时系统仍显示一切就绪；其次是登录判定双标准（cookie 与 DOM 各判各的）和预算不可配置。

## 一、数据准确性

现状与问题：
1. 新鲜度是纯时间驱动的。freshness.py 的 _ttl_days：want 2 天 / maybe 4 天 / core 7 天 / stretch 14 天 / 其余 30 天，到期才安排复核。实测死亡率：采后 1-3 天内 9/13 关闭。岗位死了但 TTL 没到，系统就一直显示就绪。
2. 计划基于只读内存快照（jd_update.py plan_from_database），设计上安全，但计划到执行之间岗位状态会漂移，执行时不复核计划里的岗位是否仍然有效。
3. 预算语义含混：计划 notes 自述"预算包含失败占位记录，不等于成功详情数"，采集数≠净增数，用户看到的 25 条可能是 25 次尝试。
4. 登录判定双标准：发送预检用 CDP cookie（wt2，可靠），采集器用 DOM 选择器（_require_login，8 秒超时，页面渲染慢就误判）。同一浏览器两个模块结论相反，15:08 的运行失败即此。
5. 发送路径发现"职位已关闭"后不回写 freshness，死岗信息在系统内丢失。

潜在风险：基于就绪状态的投递决策建立在过期事实上；失败占位与真实成功混在同一个 collected 数字里，误导后续预算决策。

## 二、更新及时性

1. 只有手动触发，无任何使用时校验。授权、确认、生成都不会触发岗位存活检查，用户第一次知道岗位死了是在发送失败那一刻。
2. 复核按 TTL 轮询，collect 后 1-3 天内的死亡无从感知，而那正是 Boss 岗位死亡的高发窗口。
3. scan_coverage 的 likely_closed 依赖列表扫描连续 miss 的间接启发式，发现路径慢且间接。

## 三、异常处理

好的部分：阶段状态机完整（completed/paused/failed/cancelled/skipped）；安全校验即停且不自动恢复；中断恢复 recover_interrupted 存在；租约防并发。
不足：
1. 停止只在阶段边界生效（executor run 循环里 stop_requested 检查在阶段之间），单阶段 25 条采集中途无法停。
2. 瞬时故障与真故障不区分：页面渲染慢导致的选择器超时被当成"未登录"直接判失败，无重试退避。
3. 失败原因对用户不可见：面板只显示"任务失败"，stop_reason 折叠在详情里，无建议动作。
4. 审核服务 HTTPServer 允许端口双绑定（SO_REUSEADDR），旧进程残留时新旧抢答，今天实际发生过。

## 四、性能表现

1. 全程单浏览器串行，固定沉睡：每个详情页 12-18 秒 settle + 任务间 _refresh_delay，一轮 20 条复核约 10-15 分钟，与页面实际响应速度无关。
2. 计划构建时把整个库备份进内存快照，当前 505 条无碍，库存上万后会变慢。
3. 无进度流式输出，长任务期间界面只有"刷新状态"手动轮询。

## 五、用户体验

1. 预算与采集范围不可见不可调：favorites/search/refresh 预算硬编码默认 25/25/20（jd_update.py:31-33，仅 CLI 参数可改），界面上无任何展示，用户原话"根本没有什么可选的"。
2. 死岗在投递界面仍显示 ready，与发送结果自相矛盾，直接消耗用户信任。
3. 运行失败只有四个字，需要自己去别处找原因。

## 改进建议（按优先级）

P0-1 投递前实时存活校验并回写 freshness。授权或执行发送前本来就要打开岗位页，把"职位已关闭"的判定结果写回 job_freshness（evidence_state=closed, closure_reason=职位已关闭，与系统既有约定一致），同时清空该岗位的确认与授权。理由：今天 9/13 死岗事故的直接教训，边际成本近零，投递决策从此建立在事实上。

P0-2 统一登录判定。以 CDP cookie 检查为主判据（与发送预检一致），DOM 选择器降级为辅助并在失败时退避重试 2 次。理由：判定互相矛盾会直接打断用户操作，且 DOM 选择器有随 Boss 改版腐化的历史（chat_btn 同类问题已发生过）。

P1-1 预算与采集范围进配置、上面板。把 favorites/search/refresh 预算移入 config.yaml，更新面板展示当前预算与关键词，允许修改后再生成计划。理由：用户明确表达困惑；库存死亡率 70% 的现实下 25/25/20 的固定预算既不够替换死岗又可能浪费复核。

P1-2 死岗即时候补。detail_refresh 阶段发现关闭岗位时，从 remaining_detail_jobs 自动递补，保证每轮净产出达标。理由：refresh 预算被死岗吃掉后本轮净产出趋零。

P1-3 失败原因与建议动作前置。任务失败时面板直接显示 stop_reason 与下一步建议（重试/检查浏览器/稍后再试）。理由：可诊断性是今天反复返工的最大成本项。

P2-1 阶段内停止与进度流。stop 生效粒度从阶段细化到条目，进度以已采 n/预算 m 形式推送。理由：长任务可观测性，避免"卡死还是在跑"的猜测。

P2-2 TTL 按实测死亡率收敛。未审阅 core 岗 TTL 从 7 天降到 2-3 天；reject 岗位 30 天复核改为不自动复核（用户判断正确：下架不会重新上架，复核预算应集中给高价值岗位）。理由：让复核预算的边际价值最大化。

P2-3 自适应等待替代固定沉睡。选择器出现即继续、总时长封顶，替代固定 12-18 秒。理由：单轮耗时直接减半，不增加风控风险（点击节奏仍保留随机化）。

P3-1 端口启动防双绑定。8765 启动时若发现已有监听进程则拒绝启动并提示，禁用 SO_REUSEADDR 行为。理由：今天发生过新旧进程抢答导致请求打到旧代码。

P3-2 执行前计划复核。execute 开始时重查计划内岗位的有效性，失效岗位标注后递补。理由：计划与执行的间隔期状态漂移。

## 落地顺序建议

先做 P0-1 和 P0-2（半天内可完成，直接消除今天两类事故的复发），然后 P1-3 与 P1-1（体验与可控性），P2 随下轮迭代，P3 择机。每项都应在 tests/ 有对应回归用例，遵守"测试先行、真实外部验收与本地结果分开记录"的既有规则。
